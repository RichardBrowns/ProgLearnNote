# 分布式理论

## 什么是CAP理论？

<img src="http://cdn.tobebetterjavaer.com/tobebetterjavaer/images/sidebar/sanfene//fenbushi-6b0609de-e2ce-4778-b76f-018af80c617f.jpg" alt="img" style="zoom:50%;" />

CAP理论是指在分布式系统中，无法同时满足一致性、可用性和分区容错性，最多满足其中两个。

- **一致性(Consistency)**：指所有节点在同一时间具有相同数据。即当一个节点更新数据后，其他节点读取数据都会返回最新的值。
- **可用性(Availability)**：指的是每次请求无论成功或者失败都要有响应，而不会让客户挂起或等待。
- **分区容错性(Partition tolerance)**：是指遇到网络分区故障，分布式系统仍需正常运行。

## 为什么CAP不可兼得？

CAP定理的核心在于网络分区的存在，分布式系统中网络分区是不可避免的，这使得系统必须在一致性和可用性之间进行权衡。

- 如果系统选择一致性（C）和分区容忍性（P），那么在网络分区发生时，为了保证一致性，系统可能需要拒绝一些请求，从而牺牲可用性（A）。
- 如果系统选择可用性（A）和分区容忍性（P），那么在网络分区发生时，系统将继续响应请求，即使这可能导致不同节点的数据不一致，从而牺牲一致性（C）。

## 什么是BASE理论？

BASE 理论是分布式系统设计中的一种方法论，与 CAP 定理相对。BASE 是 "Basically Available, Soft state, Eventual consistency" 的缩写，意为 "基本可用、软状态、最终一致性"。BASE 理论提供了一种在分布式系统中处理一致性和可用性权衡的方法，特别是在高可用性和性能要求较高的系统中。以下是对 BASE 理论的详细解释：

**基本可用（Basically Available）**

基本可用意味着系统在大多数情况提供可用服务，但不保证所有功能在所有时间都完全可用。基本可用的具体表现可以包括：

- **响应时间的延迟：**系统可能会在高负载或部分故障情况下响应时间变长。
- **功能的降级**：在某些情况下，系统可能会提供有限的功能或部分服务，而不是完全不可用。

**软状态（Soft State）**

软状态允许系统在不同节点之间的数据不完全同步，容忍短暂的不一致性。这种设计允许系统在面对网络分区或其他临时问题时仍然保持高可用性。

**最终一致性（Eventual Consistency）**

最终一致性是指系统中的所有副本最终将达到一致状态，但不要求实时一致性。最终一致性允许系统在短时间内存在数据不一致，但通过异步的方式，系统会在一段时间后达到一致。这种设计使用于需要高可用性和性能的场景，允许系统在短期不一致的情况下仍然提供服务。

**BASE理论和CAP定理的关系**

BASE理论可以看作CAP定理的一种实际应用策略。CAP定理指出在网络分区的情况下，系统必须在一致性和可用性之间进行权衡。而BASE理论倾向于选择可用性和分区容错性，牺牲强一致性，达到最终一致性。

**应用**

BASE 理论在许多实际应用中得到了广泛采用，特别是在需要高可用性和性能的系统中。以下是一些实际应用的例子：

- **社交媒体平台**：如 Facebook、Twitter 等，允许用户在短期内看到不同步的内容，但最终会达到一致。
- **电商平台**：如亚马逊，允许购物车和库存信息在短时间内不一致，但最终会同步。
- **分布式缓存系统**：如 Redis 和 Memcached，允许缓存数据在短期内不同步，但最终会一致。

**总结**

BASE 理论提供了一种在分布式系统中处理一致性和可用性权衡的方法，特别适用于需要高可用性和性能的场景。通过接受短期的不一致，系统能够在面对网络分区和其他临时问题时保持高可用性和性能。理解和应用 BASE 理论有助于设计和优化分布式系统，以满足特定应用场景的需求。

## 什么是分布式一致性？有哪些常见的分布式一致性模型？

分布式一致性是指在分布式系统当中，多个节点之间保持数据一致性的能力。常见的分布式一致性模型如下：

1. **强一致性（Strong Consistency）**：要求所有节点在任何时候都看到相同的数据状态。强一致性对系统的可用性和性能有影响，适合银行转账等对数据一致性要求高的业务场景。
2. **弱一致性（Weak Consistency）**：不保证数据一致，也不必保证多久后数据会一致
3. **最终一致性（Eventual Consistency）**：保证数据在经过一段时间后，所有节点将自动达到一致的状态

# 分布式锁

## MySQL分布式锁？

MySQL分布式锁是一种基于MySQL数据库实现的分布式锁机制，通过数据库的行锁特性，确保在分布式环境中多个进程不会同时访问同一资源。

**实现方案**

1. **基于表记录的分布式锁**

   这种方法通过在数据库中创建一张专门的锁表来实现分布式锁。锁表结构如下：

   ```sql
   CREATE TABLE `distributed_locks` (
     `lock_name` VARCHAR(255) NOT NULL,
     `lock_owner` VARCHAR(255) NOT NULL,
     `lock_time` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
     PRIMARY KEY (`lock_name`)
   );
   ```

   - `lock_name`：锁的名称，作为主键。
   - `lock_owner`：锁的拥有者，可以是节点的标识。
   - `lock_time`：锁的创建时间，用于超时判断。

2. **锁的获取**

   获取锁时，尝试向锁表中插入一条记录。如果插入成功，则表示获取锁成功；如果插入失败（因为主键冲突），则表示锁已经被其他进程持有。

   ```sql
   INSERT INTO distributed_locks (lock_name, lock_owner) VALUES ('my_lock', 'node_1');
   ```

   如果插入失败，可以通过捕获异常来判断锁是否被持有：

   ```java
   try {
       String sql = "INSERT INTO distributed_locks (lock_name, lock_owner) VALUES (?, ?)";
       PreparedStatement pstmt = connection.prepareStatement(sql);
       pstmt.setString(1, "my_lock");
       pstmt.setString(2, "node_1");
       pstmt.executeUpdate();
       // 获取锁成功
   } catch (SQLException e) {
       // 获取锁失败
   }
   ```

3. **锁的释放**

   释放锁时，删除对应的记录即可：

   ```sql
   DELETE FROM distributed_locks WHERE lock_name = 'my_lock' AND lock_owner = 'node_1';
   ```

4. **锁的超时**

   为了防止死锁，可以在获取锁时设置一个超时时间，定期检查并删除超时的锁。可以通过 `lock_time` 字段来实现：

   ```sql
   DELETE FROM distributed_locks WHERE lock_name = 'my_lock' AND lock_time < DATE_SUB(NOW(), INTERVAL 5 MINUTE);
   ```

**优缺点**

**优点**

1. **实现简单**：基于数据库的分布式锁实现相对简单，容易理解和实现。
2. **无需额外组件**：不需要引入额外的中间件，适合已有 MySQL 数据库的系统。

**缺点**

1. **性能瓶颈**：数据库操作相对较慢，性能不如基于内存的分布式锁（如 Redis）。
2. **单点故障**：数据库成为单点故障，数据库宕机会导致锁失效。
3. **并发性能**：在高并发场景下，数据库的行锁可能会成为瓶颈。

## Redis分布式锁？

基于 Redis 的分布式锁是一种高效、可靠的实现分布式锁的方式，广泛应用于需要高性能和高可用性的分布式系统中。Redis 是一个高性能的内存数据库，提供了丰富的命令和特性，使其非常适合实现分布式锁。

**实现方案**

1. **使用SETNX命令**

   Redis 提供了 SETNX（SET if Not eXists）命令，可以用于实现分布式锁。SETNX 命令只有在键不存在时才会设置键的值，并返回 1，如果键已经存在，则返回 0。

   - **锁的获取**

     ```bash
     SETNX lock_key lock_value
     ```

     - `lock_key`：锁的键名。
     - `lock_value`：锁的值，可以是一个唯一标识（如 UUID）。

     为了防止死锁，通常会为锁设置一个过期时间，可以使用 `EXPIRE` 命令：

     ```bash
     SETNX lock_key lock_value
     EXPIRE lock_key 10
     ```

     或者可以直接使用带有过期时间的 `SET` 命令：

     ```bash
     SET lock_key lock_value NX PX 10000
     ```

     - `NX`：只在键不存在时设置键。
     - `PX 10000`：设置键的过期时间为 10000 毫秒（10 秒）。

   - **锁的释放**

     释放锁时，需要确保只有锁的持有者才能释放锁。可以通过比较 `lock_value` 来实现：

     ```bash
     if redis.call("get", KEYS[1]) == ARGV[1] then
         return redis.call("del", KEYS[1])
     else
         return 0
     end
     ```

     将上述 Lua 脚本保存在 `release_lock.lua` 文件中，然后通过 `EVAL` 命令执行：

     ```bash
     EVAL "$(cat release_lock.lua)" 1 lock_key lock_value
     ```

2. **RedLock算法**

   为了进一步提高可靠性，Redis 创始人提出了 Redlock 算法。Redlock 算法基于多个独立的 Redis 实例，通过在大多数实例上成功获取锁来实现分布式锁。

   **算法步骤**

   1. 获取当前时间 `T1`。
   2. 依次向 `N` 个 Redis 实例尝试获取锁，使用相同的 `lock_key` 和 `lock_value`，并设置相同的过期时间。
   3. 计算获取锁的时间 `T2`，如果在大多数实例（至少 `N/2 + 1`）上成功获取锁，且 `T2 - T1` 小于锁的过期时间，则认为锁获取成功。
   4. 如果锁获取失败（未能在大多数实例上获取锁或时间超时），则依次释放所有实例上的锁。

   **实现代码**

   以下是一个基于 Java 的 Redlock 实现示例：

   ```java
   import redis.clients.jedis.Jedis;
   import redis.clients.jedis.JedisPool;
   import redis.clients.jedis.JedisPoolConfig;
   
   import java.util.UUID;
   
   public class RedisDistributedLock {
       private static final int LOCK_EXPIRE_TIME = 10000; // 锁过期时间，单位毫秒
       private static final int RETRY_DELAY = 200; // 重试延迟，单位毫秒
       private static final int RETRY_TIMES = 3; // 重试次数
       
       private JedisPool jedisPool;
       
       public RedisDistributedLock(String host, int port) {
       	JedisPoolConfig config = new JedisPoolConfig();
           config.setMaxTotal(128);
           jedisPool = new JedisPool(config,host,port);
       }
       
       public String acquireLock(String lockKey, int expireTime) {
           try(Jedis jedis = jedisPool.getResource()){
               String lockValue = UUID.randomUUID.toString();
               for(int i = 0; i < RETRY_TIMES; i++){
                   String result = jedis.set(lockKey,lockValue,"NX","PX",expireTime);
                   if("OK".equals(result)){
                       return lockValue;
                   }
                   Thread.sleep(RETRY_DELAY);
               }
           } catch (Exception e){
               e.printStackTrace();
           }
           return null;
       }
       
       public boolean releaseLock(String lockKey, String lockValue) {
           String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                           "return redis.call('del', KEYS[1]) " +
                           "else return 0 end";
           try (Jedis jedis = jedisPool.getResource()) {
               Object result = jedis.eval(script, 1, lockKey, lockValue);
               return "1".equals(result.toString());
           } catch (Exception e) {
               e.printStackTrace();
           }
           return false;
       }
       
       public static void main(String[] args) {
           RedisDistributedLock lock = new RedisDistributedLock("localhost", 6379);
           String lockKey = "my_lock";
           String lockValue = lock.acquireLock(lockKey, LOCK_EXPIRE_TIME);
   
           if (lockValue != null) {
               System.out.println("Lock acquired!");
               // 执行业务逻辑
               boolean released = lock.releaseLock(lockKey, lockValue);
               if (released) {
                   System.out.println("Lock released!");
               } else {
                   System.out.println("Failed to release lock!");
               }
           } else {
               System.out.println("Failed to acquire lock!");
           }
       }
   }
   ```

## Zookeeper分布式锁？

ZooKeeper 是一个分布式协调服务，广泛用于分布式系统中，其中一个常见的应用是实现分布式锁。分布式锁可以用于确保在分布式系统中，某些关键资源在同一时间只被一个客户端访问。ZooKeeper 提供了一种可靠的机制来实现这一点。

**基本原理**

Zookeeper实现分布式锁的基本原理是基于其节点（ZNode）的有序性和临时性。以下是实现分布式锁的步骤：

1. **创建锁节点**

   每个客户端在尝试获取锁时，会在指定的路径下创建一个临时顺序节点。假设锁的路径是 `/lock`，客户端会创建类似于 `/lock/lock-0000000001`、`/lock/lock-0000000002` 这样的节点。

2. **获取锁**

   客户端创建节点后，Zookeeper会返回节点的完整路径。客户端接着获取 `/lock` 路径下所有子节点的列表，并检查自己创建的节点是否是列表中序号最小的节点。如果是，则该客户端获取到锁。

3. **监听前一个节点**

   如果客户端创建的节点不是最小的，它就会找出比自己序号小的节点，并对其设置监听器（Watcher）。当比自己序号小的节点被删除时，ZooKeeper 会通知客户端。

4. **重新尝试获取锁**

   当客户端接收到前一个节点被删除的通知时，它会重新获取 `/lock` 路径下所有子节点的列表，并再次检查自己创建的节点是否是列表中序号最小的节点。如果是，则该客户端获取到锁；如果不是，则重复步骤 3。

5. **释放锁**

   客户端完成对共享资源的操作后，会删除自己创建的临时顺序节点，从而释放锁。此时，ZooKeeper 会通知下一个监听这个节点的客户端，它可以尝试获取锁。

**示例代码**

```java
import org.apache.curator.framework.CuratorFramework;
import org.apache.curator.framework.CuratorFrameworkFactory;
import org.apache.curator.framework.recipes.locks.InterProcessMutex;
import org.apache.curator.retry.ExponentialBackoffRetry;

public class ZookeeperDistributedLockExample {

    public static void main(String[] args) {
        String zkConnectionString = "localhost:2181";
        String lockPath = "/locks/mylock";

        CuratorFramework client = CuratorFrameworkFactory.newClient(
                zkConnectionString, new ExponentialBackoffRetry(1000, 3));
        client.start();

        InterProcessMutex lock = new InterProcessMutex(client, lockPath);

        try {
            if (lock.acquire(5, TimeUnit.SECONDS)) {
                try {
                    // 执行需要加锁的操作
                    System.out.println("获得锁，执行操作");
                } finally {
                    lock.release();
                }
            } else {
                System.out.println("未能获得锁");
            }
        } catch (Exception e) {
            e.printStackTrace();
        } finally {
            client.close();
        }
    }
}
```

**优点**

1. **强一致性**：Zookeeper 保证了强一致性，确保锁的获取和释放过程是安全的。
2. **高可靠性**：Zookeeper 的设计使其在节点故障时仍能继续提供服务。
3. **简单易用**：通过客户端库（如 Apache Curator），可以很方便地使用 Zookeeper 实现分布式锁。

**缺点**

1. **性能开销**：Zookeeper 的强一致性机制带来了较高的性能开销，尤其是在高并发环境下。
2. **单点瓶颈**：Zookeeper 集群的性能瓶颈可能成为系统的瓶颈，尤其是锁竞争激烈时。
3. **依赖性**：需要额外部署和维护 Zookeeper 集群。

# 分布式事务

## 什么是分布式事务？

分布式事务是指在分布式系统中，事务的操作涉及多个不同的节点或服务。为了保证数据的一致性和完整性，需要确保这些操作要么全部成功，要么全部失败。这种事务通常跨越多个数据库、消息队列、微服务等组件。

**分布式事务的特性**

分布式事务具有以下几个主要特性：

1. **原子性（Atomicity）**：事务中的所有操作要么全部完成，要么全部不完成。
2. **一致性（Consistency）**：事务完成后，系统状态必须保持一致。
3. **隔离性（Isolation）**：并发执行的事务之间不应互相影响。
4. **持久性（Durability）**：事务完成后，其结果必须持久保存。

这些特性通常被称为 ACID 特性。

## 分布式事务实现方案

### 两阶段提交协议（2PC, Two-Phase Commit）

两阶段提交（2PC, Two-Phase Commit）是一种常见的分布式事务协议，用于确保分布式系统中的所有参与节点在事务提交时保持一致性。它分为两个主要阶段：准备阶段（Prepare Phase）和提交阶段（Commit Phase）。

**两阶段提交的工作原理**

1. **准备阶段（Prepared Phase）**

   在准备阶段，事务协调者向所有参与者发送准备请求，询问它们是否可以准备提交事务。具体步骤如下：

   1. **事务开始：**事务协调者向所有参与者发送“准备请求”
   2. **事务执行：**参与者接收到请求后，执行事务操作但不提交。如果参与者能够成功执行操作，则记录日志并锁定相关资源，返回“可以提交”消息给协调者；如果不能成功执行操作，则返回“不能提交”消息。
   3. **投票结果：**协调者收集所有参与者的投票结果。

2. **提交阶段（Commit Phase）**

   在提交阶段，协调者根据投票结果决定是否提交整个事务。具体步骤如下：

   1. **决策：**
      - 如果所有参与者都返回“可以提交”，协调者向所有参与者发送“提交”（Commit）请求。
      - 如果有任何一个参与者返回“不能提交”，协调者向所有参与者发送“回滚”（Rollback）请求。
   2. **执行决策：**
      - 参与者接收到“提交”请求后，正式提交事务并释放锁定的资源，然后向协调者返回确认消息。
      - 参与者接收到“回滚”请求后，回滚事务操作并释放锁定的资源，然后向协调者返回确认消息。
   3. **完成事务：**
      - 协调者在收到所有参与者的确认消息后，事务完成。

**优点**

1. **一致性**：确保分布式系统中的所有参与者在事务提交时保持一致性。
2. **简单性**：协议相对简单，易于理解和实现。

**缺点**

1. **性能开销**：两阶段提交需要两次网络通信，增加了延迟和性能开销。
2. **单点故障**：协调者是单点故障，如果协调者在决策阶段崩溃，参与者可能会处于不一致状态。
3. **资源锁定**：在准备阶段，参与者需要锁定资源，直到事务提交或回滚，这可能导致资源长时间被占用，降低系统并发性能。
4. **网络分区问题**：在网络分区情况下，协调者和参与者之间可能无法通信，导致事务无法正常完成。

**解决单点故障的措施**

为了缓解协调者的单点故障问题，可以采取以下措施：

1. **协调者日志**：协调者在每个阶段记录日志，崩溃后可以通过日志恢复状态。
2. **超时机制**：参与者在等待协调者决策时设置超时，如果超时未收到决策，可以自行回滚事务。
3. **分布式协调者**：通过分布式算法（如Paxos或Raft）实现协调者的高可用性，避免单点故障。

**两阶段提交的实际应用**

两阶段提交广泛应用于需要保证强一致性的分布式系统中，例如：

- **金融系统**：银行转账、支付系统等需要保证资金的一致性。
- **电子商务**：订单处理、库存管理等需要保证数据的一致性。
- **分布式数据库**：跨多个节点的事务操作需要保证一致性。

### 三阶段提交协议（3PC, Three-Phase Commit）

三阶段提交（3PC, Three-Phase Commit）是对两阶段提交（2PC, Two-Phase Commit）的一种改进，旨在解决两阶段提交中的一些缺点，特别是协调者（Coordinator）单点故障导致的资源长时间锁定问题。三阶段提交通过引入一个额外的阶段，增加了协议的健壮性和容错能力。

**三阶段提交的工作原理**

1. **准备阶段（CanCommit）**

   在准备阶段，协调者向所有参与者发送准备请求，询问它们是否可以准备提交事务。具体步骤如下：

   1. **事务开始**：协调者向所有参与者发送“准备提交”（CanCommit）请求。
   2. **事务执行**：参与者接收到请求后，执行事务操作但不提交。如果参与者能够成功执行操作，则返回“可以提交”（Yes）消息给协调者；如果不能成功执行操作，则返回“不能提交”（No）消息。
   3. **投票结果**：协调者收集所有参与者的投票结果。

2. **预提交阶段（PreCommit）**

   在预提交阶段，协调者根据投票结果决定是否可以预提交事务。具体步骤如下：

   1. **决策：**
      - 如果所有参与者都返回“可以提交”，协调者向所有参与者发送“预提交”（PreCommit）请求。
      - 如果有任何一个参与者返回“不能提交”，协调者向所有参与者发送“中止”（Abort）请求。
   2. **执行预提交：**
      - 参与者接收到“预提交”请求后，记录日志并锁定相关资源，返回“预提交确认”（Ack）消息给协调者。
      - 参与者接收到“中止”请求后，回滚事务操作并释放锁定的资源。

3. **提交阶段（DoCommit）**

   在提交阶段，协调者根据预提交阶段的确认消息决定是否最终提交事务。具体步骤如下：

   1. **决策：**
      - 如果协调者收到所有参与者的“预提交确认”消息，向所有参与者发送“提交”（DoCommit）请求。
      - 如果协调者未收到所有参与者的确认消息，则向所有参与者发送“中止”请求。
   2. **执行决策：**
      - 参与者接收到“提交”请求后，正式提交事务并释放锁定的资源，然后向协调者返回确认消息。
      - 参与者接收到“中止”请求后，回滚事务操作并释放锁定的资源，然后向协调者返回确认消息。
   3. **完成事务：**协调者在收到所有参与者的确认消息后，事务完成。

**优点**

1. **减少资源锁定时间**：通过增加预提交阶段，减少了资源长时间锁定的可能性。
2. **提高容错能力**：在预提交阶段，如果协调者崩溃，参与者可以根据日志状态决定是否提交或回滚事务。
3. **避免单点故障**：在预提交阶段，如果协调者崩溃，参与者可以通过超时机制自行决定回滚事务。

**缺点**

1. **复杂性增加**：相比两阶段提交，三阶段提交的协议更复杂，增加了实现和理解的难度。
2. **性能开销**：三阶段提交需要三次网络通信，增加了延迟和性能开销。
3. **一致性保证**：虽然三阶段提交提高了容错能力，但在极端情况下仍可能出现一致性问题。

### 本地事务+补偿事务（TCC, Try-Confirm/Cancel）

TCC（Try-Confirm-Cancel）是一种分布式事务控制协议，常用于微服务架构中以确保数据一致性。TCC协议通过三个阶段来管理事务：Try阶段、Confirm阶段和Cancel阶段。这种方法提供了比两阶段提交（2PC）和三阶段提交（3PC）更灵活的控制和更高的性能。

**三个阶段**

1. **Try阶段**：
   - **目的**：预留资源并进行业务检查。
   - **操作**：在这个阶段，各个参与者会尝试执行操作并预留资源，但不进行实际的提交。通常是进行必要的业务检查和资源预留，以确保后续操作可以顺利进行。
   - **示例**：在一个银行转账操作中，Try阶段会检查账户余额是否充足，并锁定相应的金额。
2. **Confirm阶段**：
   - **目的**：确认并提交操作。
   - **操作**：如果所有参与者的Try操作都成功，协调者会通知所有参与者执行Confirm操作。在这个阶段，各个参与者会正式提交之前预留的资源，完成实际的业务操作。
   - **示例**：在银行转账操作中，Confirm阶段会正式扣除转出账户的金额并增加到转入账户。
3. **Cancel阶段**：
   - **目的**：取消操作并释放资源。
   - **操作**：如果任何一个参与者的Try操作失败，或者在Confirm阶段之前协调者决定中止事务，协调者会通知所有参与者执行Cancel操作。在这个阶段，各个参与者会释放之前预留的资源，回滚任何已经执行的操作。
   - **示例**：在银行转账操作中，Cancel阶段会释放之前锁定的金额，使账户恢复到初始状态。

**工作流程**

1. **协调者发起Try请求**：
   - 协调者向所有参与者发送Try请求。
   - 各个参与者执行Try操作，预留资源并返回Try操作结果。
2. **协调者收集Try结果**：
   - 如果所有参与者的Try操作都成功，协调者会发起Confirm请求。
   - 如果任何一个参与者的Try操作失败，协调者会发起Cancel请求。
3. **协调者发起Confirm或Cancel请求**：
   - **Confirm请求**：所有参与者的Try操作都成功，协调者向所有参与者发送Confirm请求，参与者执行Confirm操作并提交事务。
   - **Cancel请求**：任何一个参与者的Try操作失败，协调者向所有参与者发送Cancel请求，参与者执行Cancel操作并回滚事务。

**优点**

1. **灵活性高**：TCC允许在Try阶段进行复杂的业务检查和资源预留，比2PC和3PC更灵活。
2. **性能较好**：由于Try阶段只是预留资源而不提交，Confirm和Cancel阶段可以并发执行，减少了锁定资源的时间。
3. **清晰的事务边界**：TCC明确划分了各个阶段的职责，使得事务控制更加清晰。

**缺点**

1. **实现复杂**：TCC需要开发者在每个参与者中实现Try、Confirm和Cancel操作，增加了开发复杂性。
2. **资源预留问题**：在Try阶段预留资源可能会导致资源长时间锁定，特别是在高并发环境下。
3. **网络开销**：TCC需要三次网络通信（Try、Confirm、Cancel），增加了网络开销。

### 消息队列事务（Eventual Consistency with Message Queue）
